# ADR 0001: Modular monolith and core stack

- **Status:** Accepted
- **Date:** 2026-10-02

## Context

Meeting Hub ingests meeting recordings, transcribes them, identifies speakers, extracts decisions and
action items with evidence (transcript segment IDs → timestamps), and answers questions with citations.
The core differentiator is a persistent, evidence-linked ledger of decisions and action items across meetings.

The workload mixes request/response API traffic with long-running, retry-prone background work
(transcription, LLM extraction, embeddings). The team is small and the domain is still being discovered,
so module boundaries will move. We want one place to change code and one deploy, without giving up
the ability to split later.

## Decision

### Shape: modular monolith, one codebase, three processes

| Process | Entry                       | Role                     |
| ------- | --------------------------- | ------------------------ |
| web     | `apps/web` (Next.js)        | UI                       |
| api     | `apps/server/src/api.ts`    | HTTP API (Fastify)       |
| worker  | `apps/server/src/worker.ts` | Background jobs (BullMQ) |

API and worker share one package and one Docker image; the command picks the role. Domain code lives in
`apps/server/src/modules/<name>` with a public `index.ts`. Modules import each other **only through that
index**, enforced by `eslint-plugin-boundaries`. This keeps a later extraction into services mechanical.

### Stack

| Concern          | Choice                                                        | Why                                                                                |
| ---------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Language         | TypeScript (strict) everywhere                                | One language across web, API, worker and contracts                                 |
| Runtime          | Node.js 24 LTS                                                | Current LTS line; pinned in `.nvmrc` and `engines`                                 |
| Monorepo         | pnpm workspaces + Turborepo                                   | Fast, strict installs; cached task graph                                           |
| Database         | PostgreSQL 18 + pgvector, `pg_trgm`, `unaccent`               | One store for relational data, vectors and text search; native `uuidv7()` in PG 18 |
| ORM / migrations | Drizzle ORM, plain SQL migrations via drizzle-kit             | Type-safe queries; migrations are reviewable SQL                                   |
| Jobs             | Redis + BullMQ                                                | Retries/backoff, stalled-job recovery, schedulers; well-known operationally        |
| Object storage   | S3 API via `@aws-sdk/client-s3`, configurable endpoint        | Portable across AWS/R2/GCS-interop/self-hosted                                     |
| Local S3         | Garage                                                        | Lightweight, actively maintained; MinIO community edition is archived              |
| Schemas          | Zod (env config, API contracts, later AI outputs)             | Single schema language; drives validation, types and OpenAPI                       |
| API              | Fastify + `fastify-type-provider-zod` + `@fastify/swagger`    | Fast, typed routes; OpenAPI generated from the same Zod schemas                    |
| Web              | Next.js App Router, Tailwind, shadcn/ui                       | Mainstream React stack; typed client generated from OpenAPI (`openapi-typescript`) |
| Logging          | pino JSON, `request_id` on every API line, redaction          | Structured, cheap; meeting content must never be logged                            |
| Errors           | `AppError` hierarchy → RFC 9457 `application/problem+json`    | Stable `code` for clients; `RetryableError`/`PermanentError` drive worker retries  |
| Testing          | Vitest; Testcontainers for Postgres/Redis                     | Real dependencies in integration tests, no shared test DB                          |
| Feature flags    | In-house service over a `feature_flags` table + env overrides | Every feature ships dark; no vendor dependency yet                                 |

### Conventions that follow from this

- Primary keys are UUIDv7 (time-ordered, index-friendly), generated by Postgres.
- Cross-module side effects go through the `domain_events` transactional outbox (table exists; dispatcher later).
- Every new feature is gated by a flag registered in `modules/platform/flags/definitions.ts`.
  _Amended 2026-10-04:_ user-facing features under development get a flag; foundational CRUD that other
  features depend on (e.g. meetings) does not.

## Consequences

- **+** One deploy, one CI pipeline, refactors across modules are a single PR.
- **+** API and worker scale independently despite sharing code.
- **+** OpenAPI and the web client are generated from the same Zod schemas, so they cannot drift (CI checks this).
- **−** Boundaries are enforced by lint, not by process isolation; a bad merge can still couple modules if
  the rule is disabled. Reviews must treat boundary-rule suppressions as architectural changes.
- **−** Redis is a hard dependency for background work; it must run with `noeviction`.
- **−** PostgreSQL 18 is required for native `uuidv7()` (the brief allowed 16+). Supporting 16/17 would mean
  generating IDs in the application or via an extension.

## Alternatives considered

- **Microservices from day one** — rejected: premature distribution cost for an unsettled domain.
- **Prisma** — rejected in favour of Drizzle's SQL-first migrations and lighter runtime.
- **pg-boss / Postgres-only queue** — viable; BullMQ chosen for its mature retry, rate-limit and flow features
  needed by multi-step AI pipelines.
- **MinIO for local S3** — community edition archived; Garage chosen (SeaweedFS was the fallback).
